# Manual staging rollback — implementation record

## Approved scope

Issue [#169](https://github.com/PEERS-P25-02/ProjectPeerEvaluation-P25-02/issues/169) covers staging-only restoration to a selected verified-success image pair. The requester approved the local Stage 01 requirements and Stage 02 plan after [PR #187](https://github.com/PEERS-P25-02/ProjectPeerEvaluation-P25-02/pull/187) removed selective CD. The initial implementation added a manual dispatch workflow coordinated with automatic CD. Automatic CD remains enabled; there is no deployment hold or automatic reversal.

The workflow reads only an annotated `staging-success/cd-*` tag as data. It validates the versioned manifest, exact GHCR digests, configured staging service identity, and busy state before any Render mutation. It redeploys backend then frontend by digest, requires new Render deploy IDs to become `live` on those digests, checks backend health, and runs the three current staging smoke tests. A fully verified rollback succeeds only after deployment and smoke evidence match the selected source SHA and exact digests. The Actions summary and bounded redacted artifact are the rollback outcome record; rollback does not write a manifest, tag, or GitHub Release. CD continues to write its existing `staging-success/cd-*` tags. It does not read or move the retired `staging-last-success` marker.

## Coordination and limits

CD and rollback share the `cd-staging-images` Actions group with `cancel-in-progress: false` and `queue: max`. Read-only preflight rejects invalid dispatch/tag data; the rollback mutation job may wait behind a running CD. Once admitted, it checks configured Render service identity and active/queued deploy status before mutation. A CD queued during rollback may deploy immediately after it and replace the restored images; the requester explicitly accepted that another rollback may then be necessary. `queue: max` permits at most 100 pending runs and orders by time waiting, so dispatch order is not guaranteed. An external Render deployment is outside the Actions group.

In the original implementation, rollback tag writes were non-force and verified against the remote object ID. GitHub currently has no tag ruleset preventing a privileged writer from editing or deleting a CD history tag. A selected tag's earlier smoke success does not guarantee that its images remain available or that current MongoDB Atlas data and external settings are compatible. A partial failure leaves any already restored images in place for investigation.

## Simplified rollback outcome (2026-11-15)

The follow-up implementation accepts only verified annotated CD tags and removes rollback success-manifest/tag creation and the workflow Git write permission. Before the rollback job can succeed, a final gate cross-checks both new live deploy IDs, service IDs, exact target digest refs, backend HTTP 200/`OK` health, and all three smoke checks against the selected target SHA and digest refs. The always-run summary and redacted artifact report outcome and phase, target tag/SHA/digests, new deploy IDs/statuses, health, and available smoke results, including partial failures. Local workflow and script checks do not establish hosted rollback behavior; a new hosted rehearsal remains necessary.
